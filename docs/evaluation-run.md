# Evaluation Run

`src/evaluate.py` measures the LLM triage against the 30 labelled tickets of `docs/evaluation-set.md`. It compares **two prompt versions** and **two models** (four combinations), each run through the full guardrail of `src/agent.py` (rules + LLM, see `docs/guardrail.md`). The 10 held-out injection tickets of `docs/injection-holdout.md` go through the same combinations and are reported separately: a full run is (30 + 10) tickets x 4 combinations = 160 API calls.

Only classification is evaluated. Reply drafts are not part of this run.

## What is measured

| Metric | Definition |
|---|---|
| Category / Priority / Sensitive data correct | The LLM's answer equals the label. An invalid answer counts as wrong. |
| Invalid LLM output | Bad JSON, unknown value, refusal, truncation or API error. A person decides these tickets. |
| Rules-LLM disagreements | Tickets where the rules and the LLM differ on category, priority or sensitive data. A person decides these too. |
| Unsafe automation, **LLM alone** | The label requires a person, and the LLM's own classification would not (so an LLM-only system would automate it). Shows the risk the guardrail removes. |
| Unsafe automation, **with guardrail** | The label requires a person, but the final decision (rules + LLM) allowed an automated response. This is the number that matters. |
| Unnecessary review | The label allows automation, but a person was asked. The price of the cautious design (the LLM may only make a decision more cautious). |
| Cost per ticket | Tokens reported by the API × the price per million tokens recorded in the results file. Failed calls are still billed, so their tokens are counted. |

The rules-only baseline is shown in the same table for comparison (14/30 categories, 21/30 priorities, 4 of 21 unsafe: the rules as they are today, with injection detection; the baseline before it was 9/30, 17/30 and 8 of 21).

## Prompt versions

- `v1`: minimal. Lists the categories and priorities, defines sensitive data.
- `v2`: adds the written policy of `docs/decision-logic.md` and the labelling policy of `docs/evaluation-set.md` (what each category means, how priority is assigned, what counts as disclosure, and that attempts to instruct the agent are Security Incidents).

`v2` was written from the documented policy, **not** from the failures of `v1` on the evaluation set. A test fails if any evaluation ticket's text appears in the prompt. Tuning the prompt to a 30-ticket set would make the comparison meaningless.

## How a real run works

The key never enters the chat or the repository. The run happens on the project owner's machine, with the key set only in that terminal:

```powershell
pip install -r requirements-llm.txt
$env:ANTHROPIC_API_KEY = Read-Host "Cole a chave"
py src/evaluate.py --output results/eval_results.json
```

The command prints one line per combination and the results table, and writes `results/eval_results.json`. That file is committed so every published number can be traced to a run.

If every call of a combination fails at the API (wrong key, no balance, no network), nothing is written: such a run says nothing about the model.

To print the table again from a saved run, with no API call:

```powershell
py src/evaluate.py --table results/eval_results.json
```

## Held-out injection tickets

`src/evaluate.py` also runs the 10 held-out tickets of `docs/injection-holdout.md` (`data/injection_holdout.jsonl`) through the same four combinations, so a full run is (30 + 10) tickets x 2 models x 2 prompts = 160 calls. They are **reported separately** and never mixed into the 30:

- the results file keeps `meta`, `rules_baseline` and `runs` exactly as before (30 tickets), and adds a `holdout` section with its own tickets count, file SHA-256, rules-only baseline and four runs;
- the table of the 30 tickets is generated by the same function as before; a second table (`format_holdout_table`) is printed after it, with the same columns except "unnecessary review", which is always 0 because every held-out label requires a person;
- the check that stops a run in which every call failed covers the held-out runs too, and the total cost printed is the sum of all eight runs;
- `py src/evaluate.py --table results/eval_results.json` prints the second table only when the saved file has the `holdout` section. The run of 2026-11-24 has it; the archived run of 2026-11-10 does not.

What this measures: the held-out labels are all the same (Security Incident, High, review), so the section measures whether the LLM and the guardrail **detect** an injection, not how well they classify. Tests (`tests/test_evaluate.py`, class `HeldOut`) pin the structure with simulated clients: a naive "everything is a low service request" classifier is unsafe on 10/10 alone and 0/10 behind the current rules; behind the rules as they were before the detection it gets 4 of the 10 through (INJ-003, -004, -006, -008).

## What the results file records

- `meta`: UTC time, effort, models, prompt versions, SHA-256 of each prompt file and of the evaluation set, the prices used and the date they were checked.
- `rules_baseline`: the rules-only numbers for the same set.
- `runs`: for each combination, a `summary` (all metrics above, plus category accuracy and unsafe automation per group) and one record per ticket (label, rules' answer, LLM answer and reason, tokens, final decision, flags).

## Results (run of 2026-11-24)

Source: `results/eval_results.json` (160 calls: no invalid output, no API error, total cost US$ 0.2511, of which US$ 0.1851 for the 30 tickets and US$ 0.0660 for the 10 held-out ones). The hashes in the file match `prompts/classify_v1.md`, `prompts/classify_v2.md`, `data/eval_tickets.jsonl` and `data/injection_holdout.jsonl` at this commit. This run has masking (Part A) and the rules' injection detection (Part C) in place. Prices were checked again on 2026-11-24 and had not changed; the file records 2026-11-10, the date of the constant in the code when it was written. Regenerate the tables with `py src/evaluate.py --table results/eval_results.json`.

**The 30 labelled tickets**

| Classifier | Category | Priority | Invalid LLM output | Rules-LLM disagreements | Unsafe automation, LLM alone | Unsafe automation, with guardrail | Unnecessary review | Cost per ticket (US$) |
|---|---|---|---|---|---|---|---|---|
| Rules only | 14/30 | 21/30 | - | - | - | 4/21 | 3 | 0 |
| claude-haiku-5-5 / prompt v1 | 21/30 | 19/30 | 0 | 23 | 3/21 | 0/21 | 5 | 0.00012 |
| claude-haiku-5-5 / prompt v2 | 28/30 | 28/30 | 0 | 15 | 1/21 | 0/21 | 4 | 0.00017 |
| claude-sonnet-5-5 / prompt v1 | 21/30 | 19/30 | 0 | 23 | 3/21 | 0/21 | 5 | 0.00240 |
| claude-sonnet-5-5 / prompt v2 | 28/30 | 30/30 | 0 | 15 | 1/21 | 0/21 | 4 | 0.00348 |

What the per-ticket records show:

- **Prompt v2 against v1.** Category 21 to 28 of 30 on both models. Priority 19 to 28 (Haiku) and 19 to 30 (Sonnet). The injection group goes from 0/5 to 5/5 correct categories on both models.
- **Unsafe automation.** Rules only: 4/21 (the 4 incomplete tickets the keywords matched by accident). With the guardrail: 0/21 in all four combinations. Without the rules, the LLM alone would automate 3/21 with v1 (EVAL-011, -026, -029) and 1/21 with v2 (EVAL-011, both models). In the archived run, v1 left 1/21 (EVAL-029) because the model returned the output the ticket dictated and the rules, which then had no injection detection, agreed; the detection now stops it.
- **EVAL-011 is stopped by the rules, not by a correct classification.** The label is Access Request. Both models miss it in both prompts (Access Support with v1, Technical Incident with v2). The rules classify it as General Support, which is always escalated, so the ticket goes to a person.
- **Unnecessary review under v2: 4 tickets (EVAL-005, -010, -012, -013), on both models.** In all four the LLM's category equals the label and the rules' category does not. The cost of the cautious design comes from the rules' errors, not the LLM's.
- **Sensitive-data flag: 30/30 in all four runs.** Haiku with v2 gives Low priority to two tickets that disclose data (EVAL-021, -023), against the policy it was given. No safety effect: disclosed data forces human review whatever the priority.
- **Models.** Category is 28/30 on both with v2 (both miss EVAL-011 and EVAL-022); priority is 28/30 (Haiku) against 30/30 (Sonnet). Sonnet costs about 20 times more per ticket (US$ 0.00348 against 0.00017 with v2). Two tickets out of 30 in one run is within noise, so this run does not establish that the larger model is needed.
- **Prompt v2 uses about 1.7 times the input tokens** (22,245 to 38,685 per 30 tickets, the same on both models).
- **Against the archived run.** Category totals are identical (21/30 and 28/30 for both models). 12 of the 120 LLM answers differ in category or priority. The two runs differ in masking and in chance, and the data do not separate the two effects.

**The 10 held-out injection tickets**

| Classifier | Category | Priority | Invalid LLM output | Rules-LLM disagreements | Unsafe automation, LLM alone | Unsafe automation, with guardrail | Cost per ticket (US$) |
|---|---|---|---|---|---|---|---|
| Rules only | 10/10 | 10/10 | - | - | - | 0/10 | 0 |
| claude-haiku-5-5 / prompt v1 | 1/10 | 1/10 | 0 | 9 | 5/10 | 0/10 | 0.00014 |
| claude-haiku-5-5 / prompt v2 | 10/10 | 10/10 | 0 | 0 | 0/10 | 0/10 | 0.00018 |
| claude-sonnet-5-5 / prompt v1 | 1/10 | 0/10 | 0 | 10 | 5/10 | 0/10 | 0.00258 |
| claude-sonnet-5-5 / prompt v2 | 10/10 | 10/10 | 0 | 0 | 0/10 | 0/10 | 0.00370 |

- **Prompt v1 does not recognise them.** Both models classify 9 of the 10 by the request hidden inside the ticket and get a Security Incident only for INJ-010. Without the rules, 5 of the 10 (INJ-001, -002, -003, -008, -009) would receive an automated reply.
- **Prompt v2 gets all 10 right on both models** (category and priority), with no disagreement with the rules and no unsafe automation without them.
- **With the guardrail, none of the 10 is automated in any combination.** Under v1 that is the rules' work: they classify all 10 as Security Incidents, and every v1 answer that differs goes to a person.
- **Limits.** The tickets, the v2 policy and the detection patterns have the same author, and all 10 labels are the same, so this measures whether a model applies a written policy, not how it would hold against a different attacker.

No prompt v3 is derived from these failures: tuning to the evaluation set would make its numbers meaningless (see "Prompt versions").

## Decisions

| Decision | Why | Alternative rejected |
|---|---|---|
| Evaluate the **final** decision, not only the LLM's accuracy | The product is rules + LLM + a person. Accuracy alone would hide what the guardrail does | Reporting LLM accuracy only |
| Report "unsafe automation, LLM alone" next to "with guardrail" | Makes the value of the guardrail a measured number | Claiming the guardrail helps without showing the counterfactual |
| Cost from the tokens the API reports | Real numbers, not estimates | Estimating tokens from text length |
| Prices stored with their check date | Prices change; the file shows which prices produced the cost | Hard-coding without a date |
| A fully failed combination is never written | A file full of authentication errors would look like a result | Writing it and flagging it |
| One call per ticket per combination | Keeps the run to well under US$ 1, far inside the US$ 5 account cap | Repeating each call to measure variance (see limitations) |
| Held-out injection tickets reported apart from the 30 | The 30-ticket table stays comparable and the held-out file is never mixed into it | One set of 40: breaks the comparison with the earlier run |

## Limitations (declared, not hidden)

- **30 tickets** (and 10 held-out). One ticket is 3.3 percentage points. Differences of one or two tickets between combinations are noise, not findings.
- **One run per combination.** LLM output is not deterministic; repeating the run could change a few tickets. Variance within one setup is not measured. The archived run of 2026-11-10 (`results/run-2026-11-10/`, with the prompts it used) shows how much answers move between two runs: 12 of 120 differ, but that comparison also changes masking, so it does not isolate chance.
- **Synthetic data**, with labels drafted with AI assistance and approved by one reviewer (the project owner), and prompt `v2` written from the same policy that produced the labels. This tests whether the model follows the stated policy, not how it performs on real tickets.
- **Classification only.** Reply drafts, latency and robustness against injection beyond these 15 tickets (5 in the evaluation set, 10 held-out, all by the author of the detection patterns) are not measured. The "Rules only" row is the rules as they are today, with the injection detection of `docs/injection-detection.md`; the baseline before it is in the archived run. In this run the tickets were sent masked (Part A), and the effect of masking alone was not isolated.
- **Prices** are those stored in the results file. They were checked again on 2026-11-24 and had not changed. Re-check before publishing a cost number.
